# Foundational Research Questions

**Status:** Research backlog, not answered doctrine.

## A. Product definition

- What makes a product problem sufficiently validated to justify implementation?
- Which assumptions must be tested before build?
- How should jobs-to-be-done, desired outcomes and non-goals be represented?
- What evidence is strong enough to change approved scope?
- How should first-tenant learning be separated from reusable product truth?
- When should commercial viability influence MVP scope?

## B. Premium product quality

- What should "premium" mean beyond visual polish?
- Which qualities are universal versus product-specific?
- What makes software understandable, trustworthy and learnable?
- What evidence demonstrates a journey is complete?
- Which non-ideal UI states are universally important versus context-dependent?
- How should content/microcopy quality be judged without standardizing brand personality?

## C. Design and UX

- Which usability principles are robust across product categories?
- Which accessibility requirements should be non-negotiable?
- How should design systems balance consistency with product differentiation?
- When do familiar interaction patterns improve trust, and when is novelty appropriate?
- What should remain deliberately product/brand-specific?
- What evidence is sufficient to approve an information architecture or critical user flow?

## D. Engineering simplicity

- How do experienced teams distinguish useful abstraction from premature abstraction?
- When is temporary duplication safer/simpler than extracting shared code?
- What signals indicate architecture/code has become unnecessarily complex?
- How should maintainability be evaluated without line count as a proxy?
- When is a dependency/vendor justified?
- What evidence justifies building shared cross-project infrastructure?

## E. Architecture and scaling

- When is a modular monolith the better starting point?
- What evidence justifies adding services, queues, caches, databases, warehouses or regions?
- How should reversibility and migration paths influence architecture choice?
- What minimum observability/recovery capability is required by maturity/risk level?
- How should vendor lock-in be assessed economically rather than ideologically?
- What should scale triggers look like before real usage exists?

## F. Security and privacy

- Which secure-development controls should be universal?
- Which controls should scale with data sensitivity and action consequence?
- What constitutes sufficient authorization evidence?
- What privacy/data-minimization principles should govern AI-assisted products?
- When may a risk be accepted, and by whom?
- Which security findings must always block release?

## G. AI-assisted development

- Which development responsibilities may AI perform autonomously?
- Which product/architecture/security decisions require human confirmation?
- How should AI-generated code be reviewed differently, if at all?
- How should prompt injection, tool misuse, sensitive-data leakage and excessive agency be tested?
- What evidence is required before an agent gains write/consequential authority?
- How should model/provider neutrality be balanced against simplicity and cost?
- How should AI evaluation quality be measured at different product stages?

## H. Testing and release

- What testing is required by risk/change type?
- What must be proven before a prototype becomes a production system?
- What constitutes sufficient rollback/recovery evidence?
- How should release blockers differ for prototype, production and high-risk products?
- Which production readiness checks materially reduce incidents versus creating ritual?

## I. Operations and economics

- What operational disciplines are necessary from the first production release?
- What costs must be measured from day one?
- How should support burden and operational complexity enter feature decisions?
- What evidence should trigger infrastructure optimization or migration?
- How should SLOs/error budgets be introduced proportionally?

## J. Repository and knowledge architecture

- What makes a repository easy for both people and models to navigate?
- Which records should be canonical versus historical?
- How should stale/superseded knowledge be retained without confusing authority?
- When should repeated project learning be promoted into reusable studio knowledge?
- What evidence justifies shared-library extraction?

## K. Doctrine governance itself

- Which principles are durable enough to become doctrine?
- Which guidance belongs in standards versus playbooks?
- How should doctrine changes be versioned and reviewed?
- What evidence should be required to overturn an existing principle?
- How frequently should foundational doctrine be revalidated?
