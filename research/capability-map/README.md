# Product-Development Capability Discovery

**Status:** Research workspace — not an adoption list  
**Purpose:** Discover which disciplines, practices, tools, technologies, connectors and feedback systems Admonk may need to repeatedly produce high-quality software with AI assistance.

## Core distinction

```text
Principle
= what should be true

Practice
= how the work should be performed

Tool
= what helps perform the practice

Technology
= what enables it technically

Connector
= what lets the Supervisor or a specialist inspect/control an external system
```

Do not mix these layers.

A tool must serve a researched practice.
A practice must support an approved principle.
A connector must have an explicit inspection/action purpose and permission boundary.

## Central rule

> **Admonk should standardize quality feedback loops, not standardize a fixed technology stack.**

## Research outputs

This track should answer:
- which capabilities already exist;
- which capabilities are missing;
- which are duplicate/overlapping;
- which are only needed conditionally;
- which tools/technologies deserve evaluation;
- which feedback loops each capability closes;
- which maturity/risk level justifies adoption.

Nothing in this directory grants adoption authority.
